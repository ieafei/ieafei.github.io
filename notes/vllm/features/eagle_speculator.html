深入剖析 vLLM 中 EAGLE 投机解码的执行链路：propose → execute_model → rejection_sample → propose 循环，以及 KV cache 写入策略

跨步调用流程（Step N → Step N+1）

Step N: speculator.propose() → 生成 draft_tokens[0..K-1]，存入 req_states.draft_tokens Step N+1: execute_model() └── prepare_inputs() └── combine_sampled_and_draft_tokens() ├── input_ids = [..., last_sampled, draft_0, draft_1, ..., draft_K-1] └── logits_indices = [每个 req 的 logits 位置] └── target_model.forward(input_ids) ← 一次 forward 同时 verify 所有 draft tokens sample_tokens() └── self.sample() → rejection_sampler(logits, speculator.logits) ← 逐个验证，接受/拒绝 └── speculator.propose() → 生成下一轮 draft_tokens

关键设计：每一轮的 propose() 都依赖上一轮 target model forward 产出的 hidden states，这是 EAGLE 区别于普通 spec decode 的核心。

🔧EAGLE 在 Model Runner 中的三阶段执行

设定一个具体场景作为主线：

  • 已生成 100 个 token：tok[0..99]
  • 上一轮 sample 出的 last_sampled：L（即 tok[99]）
  • 上一轮 propose 的 3 个 draft：d1, d2, d3
1 execute_model — Target Model 一次 Forward

将 last_sampled + draft tokens 一起送入 target model，同时验证所有 draft

# 输入张量布局（query_len = 4） input_ids: [L, d1, d2, d3 ] positions: [99, 100, 101, 102] KV 读 (旧): slot 0 ~ 98 # 已存在 KV 写 (新): slot 99 ~ 102 # 全部立即写入！ output: [h0, h1, h2, h3] # shape [4, hidden_size]

⚠️ 关键时刻：L 在这一轮才正式参与计算并写入 KV——上一轮 sample 它的时候只是从上一步 hidden 走 lm_head 得到了 token id，并没有让 L 作为 input 走过 forward。

↓
2 Rejection Sample — 逐位验证 Draft Tokens

用 hidden states 计算 logits，对每个 draft 决定 accept 或 reject

位置用到的 hidden验证目标结果
99 h0 验证 d1 ✅ 接受
100 h1 验证 d2 ✅ 接受
101 h2 验证 d3 ❌ 拒绝，从 h2 重采样得到 t_bonus
102 h3 — 🗑️ 作废
# 状态更新 num_sampled = 3 # d1, d2, t_bonus num_rejected = 1 # d3 last_sampled = t_bonus # 写入 req_states.last_sampled_tokens all_token_ids[100..102] = [d1, d2, t_bonus] # 提交到状态 num_computed_tokens = 103
最终接受 d1 d2 t_bonus

3 speculator.propose() — 生成下一轮 Draft

复用 target model 的 hidden + 处理后的 input_ids，喂给 draft model 推理出新一批 draft

3.1 传参

last_hidden_states = [h0, h1, h2, h3] # 全传，shape [4, H] num_sampled = 3 num_rejected = 1 # 用这个让 kernel "逻辑剔除" h3 last_sampled = t_bonus

3.2 Kernel 内 input_ids 左移

# target 输入 target input_ids: [L, d1, d2, d3] ↓ ↓ ↓ # 左移 1 位（每个 input 接收下一位 token） draft input_ids: [d1, d2, ?, ?] ↑ 写入 t_bonus (last_sampled) # 最终 draft 输入 draft input_ids: [d1, d2, t_bonus, d3(残留无用)] hidden 不动: [h0, h1, h2, h3] # 有效长度 有效 query_len = 4 - num_rejected = 3 last_token_index 指向位置 2（即 (t_bonus, h2)）

💡 错位拼接的本质：draft model 拿 (token[i+1], hidden[i]) 做输入，目的是让它通过已有的下一个 token + 上一步压缩的语义，预测出 token[i+2]。

3.3 Draft Model Prefill 整体 Forward

input_ids: [d1, d2, t_bonus, d3残留] hidden: [h0, h1, h2, h3] ↓ embed(input_ids) ⊕ hidden # EAGLE 的二元组拼接 ↓ embed_in: [E(d1)⊕h0, E(d2)⊕h1, E(t_bonus)⊕h2, E(d3残)⊕h3] ↓ EAGLE 单层 transformer (self-attention + FFN) ↓ attention 把这 4 个位置的 K/V 写入 draft KV cache slot 99~102 ↓ out: [hd0, hd1, hd2, hd3 垃圾] # shape [4, H] # 只取最后一个有效位置的 hidden sample_hidden_states = last_hidden_states[last_token_indices] # 只取 hd2 # 走 lm_head + sample，产生第一个 draft self.draft_tokens[:num_reqs, 0] = self.sample_draft(...) # 把 hd2 保存下来，给 multi-step decode 第 2 步用 self.hidden_states[:num_reqs] = hidden_states[last_token_indices]

3.4 Multi-step → _generate_draft 自回归

从 step 1 开始，draft model 不再依赖 target 的 hidden，而是用自己上一步产出的 hd 继续推理下一个 token。这就是 EAGLE 自回归的关键——target 给的语义先验只在 step 0 用过一次，从 step 1 开始全靠 draft 自己。

❓核心问题深度解析

Q 为什么 draft model 要以 (token, hidden_state) 二元组作为输入去计算 draft token？
A

原因 1：避免重复计算 — 直接复用 target model 已经计算好的 hidden states，节省一次完整的 deep transformer forward。

原因 2：弥补 draft model 的能力差距 — draft model 网络结构层数远少于 target model，自己计算出来的隐藏层特征信息不如 target 计算好的 hidden states 有效。借用 target 的 hidden 相当于"站在巨人肩膀上"。

Q 为什么 draft model 的输入是 token[i+1], hidden_states[i]（错位拼接）？
A

因为 draft model 需要预测 token[i+2]。要预测这个新 token，最直接的输入就是："实际的下一个 token"（token[i+1]） + "上一步浓缩的语义信息"（hidden[i]）。

(token[i+1], hidden[i]) ↓ FC 层（融合二元组） ↓ 1 层 transformer ↓ draft_hidden[i+1] ↓ lm_head ↓ token[i+2]

注释：token[i+1] 是实际的下一个 token；hidden[i] 是上一步的"压缩信息"。两者拼接后才能正确指向 token[i+2]。

Q target model 在 execute_model 一次 forward 中存储的 KV cache，是否要等 draft token 确定 accept 后才真正写入？
A

核心结论：KV cache 在 forward 时就直接全部写入了，不会等 accept 结果。target model forward 一旦执行完，所有 query 位置（包括将来会被拒的位置）的 K/V 都已经写入物理内存了。没有任何"等 accept 后才提交"的逻辑。

这种激进策略的安全性由以下三点保证：

① 已 accept 的 KV 是有效的

它们对应的 token 真正被采纳，可以正常被后续步骤读取。

② 被拒的"垃圾 KV"会被下一轮覆盖

# 下一轮的 forward input_ids: [t_bonus, d1_new, d2_new, d3_new] positions: [102, 103, 104, 105] slot 写入: slot 102 (覆盖!), slot 103, 104, 105

③ 在被覆盖之前，垃圾 KV 也读不到

Postprocess 之后 num_computed_tokens 推进到 102（即"已提交的最后一个 token 是位置 101 的 d2"，加上 t_bonus 在 102 这个位置后等于 103，根据 vLLM 状态机推进规则）。下一轮 attention 计算 seq_lens 时，超出范围的 slot 不会进入合法可读区间。

✅ 结论：attention 通过 seq_lens 控制可见范围，越界的 KV 永远不会被读到。所以"先写后过滤"是完全安全的，且节省了一次条件分支判断的开销。

Q target model 与 draft model 共用一个 KV cache 存储地址吗？
A

否。在 EAGLE 方法中，draft model 拥有自己独立的 KV cache 存储空间。两者通过共享 block_tables（逻辑映射表）来协调，但物理内存是完全分离的。

━━━━━━━━ GPU 显存布局 ━━━━━━━━
▶ target KV cache
shape: [num_blocks, 32 layers, 2, ...] 写入者: target.forward slot 0 .. max_model_len 共用同一块物理内存
▶ draft KV cache (独立!)
shape: [num_blocks, 1 layer, 2, ...] 写入者: draft.forward 跟 target 完全不同的物理内存 prefill 写: slot 99 ~ 102 step=1 写: slot 102 (覆盖 d3 残留) step=2 写: slot 103

共享 block_tables（逻辑映射表）
draft / target 各自的 attention layer 通过自己的 kv_cache 张量指针访问对应物理内存

设计动机：target 是 32 层大模型，draft 是 1 层小模型，两者的 KV shape 完全不同（layer 数差异巨大），物理上无法共用同一块内存。但逻辑上的 slot 编号可以对齐（都用 position id 作为 slot 索引），通过共享 block_tables 实现高效协同。

Q seq_lens 变量是什么含义？
A

seq_lens[i] = 第 i 个 req 在本次 attention forward 时，可以从 KV cache 中读取的有效 K/V 长度（包括本次新写入的 query 部分）。

seq_lens[i] = num_computed_tokens[i] + query_len[i] = "已经在 KV cache 里的旧 token 数" + "本次新写入的 token 数"

这个变量是 attention kernel 用来生成 causal mask 的关键依据——超出 seq_lens 范围的位置一律置为 -inf，从而保证不会读到"未来的"或者"被作废的"垃圾 KV。

Q slot_mapping 是什么？
A

slot_mapping[i] = 本次 forward 中第 i 个 token 在 KV cache 中应该写入（或读取）的物理 slot 编号。

它是从"逻辑 position id"到"物理内存 slot"的一层间接映射，配合 PagedAttention 的 block 机制使用：

逻辑 position: 99, 100, 101, 102 ↓ block_tables 映射 物理 slot: slot_a, slot_a+1, slot_b, slot_b+1 # 跨 block 时不一定连续

有了 slot_mapping，attention kernel 可以直接通过 slot 编号读写对应的物理内存，而不需要每次都查 block_tables。

📝总结

EAGLE 的三个关键设计

  1. Hidden state 复用：draft model 直接吃 target 的 hidden state，避免重复深度计算，同时弥补小模型的能力差距
  2. 错位拼接 (token[i+1], hidden[i])：用"实际下一个 token"+"上一步压缩信息"二元组，让 draft 1 层网络也能预测出 token[i+2]
  3. Multi-step 自回归：step 0 借用 target hidden，step 1+ 全靠 draft 自己产出的 hidden，实现连续 K 个 draft token 的高效生成

KV cache 关键边界

方面结论
写入时机 target forward 时就立即全部写入，不等 accept 结果
垃圾 KV 处理 下一轮直接覆盖；覆盖前由 seq_lens 控制不可读
target / draft 关系 物理内存完全独立，但通过 block_tables 共享逻辑映射
可见范围控制 seq_lens（causal mask 边界）+ slot_mapping（物理 slot 映射）

✅ 核心箴言：EAGLE 的高效来自三个"省"——省 hidden 计算（复用 target）、省 forward 次数（一次 verify K 个 draft）、省条件分支（KV 写入不判断 accept，靠 seq_lens 兜底）。
