vLLM generate() 总体流程

深入追踪 llm.generate() 从用户调用到输出返回的完整执行路径

🎯背景与动机

llm.generate() 是 vLLM 离线推理的核心入口。用户传入 prompts 和 sampling_params，vLLM 内部完成 tokenization → 请求注册 → 调度 → 模型执行 → 采样 → detokenize → 停止检查 → 输出排序，最终返回有序的 RequestOutput 列表。

理解这条完整链路，是深入学习 vLLM 调度器、KV Cache 管理、投机解码等高级特性的基础。

💻基本用法

from vllm import LLM, SamplingParams # Initialize the engine llm = LLM(model="Qwen/Qwen2.5-7B-Instruct") # Define sampling parameters sampling_params = SamplingParams(temperature=0.8, top_p=0.95, max_tokens=256) # Generate outputs = llm.generate( ["Explain vLLM in one sentence.", "What is PagedAttention?"], sampling_params ) for output in outputs: print(output.outputs[0].text)

🔍逐步详解

Step 1-3: 请求预处理与注册

用户调用 llm.generate() 后，内部通过 OfflineInferenceMixin._add_completion_requests 对每个 prompt 进行处理：

return self._render_and_add_requests( prompts=( self._preprocess_cmpl_one( prompt, tokenization_kwargs, mm_processor_kwargs=mm_processor_kwargs, ) for prompt in maybe_tqdm( seq_prompts, use_tqdm=use_tqdm, desc="Rendering prompts", ) ), params=seq_params, lora_requests=seq_lora_requests, priorities=seq_priority, )

关键点：_preprocess_cmpl_one 负责将原始 prompt 格式化并 tokenize；_render_and_add_requests 将处理后的请求通过 self._add_request 注册到 LLM Engine 中。

Step 4: Engine 主循环

_run_engine() 是一个 while 循环，持续调用 llm_engine.step() 直到所有请求完成：

while self.llm_engine.has_unfinished_requests(): step_outputs = self.llm_engine.step() for output in step_outputs: assert isinstance(output, output_type) if output.finished: outputs.append(output) return sorted(outputs, key=lambda x: int(x.request_id))

engine_core.step_fn(): 调度 → 执行 → 更新

这是每一步推理的核心，完成 "Schedule, Execute, and Make Output" 三件事：

# Schedule: decide which requests to run this step scheduler_output = self.scheduler.schedule() # Execute: run model forward pass future = self.model_executor.execute_model(scheduler_output, non_block=True) model_output = future.result() # Update: process model output, update scheduler state engine_core_outputs = self.scheduler.update_from_output( scheduler_output, model_output )

返回的 EngineCoreOutputs 包含每个请求的新 token、是否结束、scheduler 统计等信息。

model_executor 层级结构：model_executor 在初始化时会实例化 Worker，Worker 再实例化 ModelRunner，形成三层结构：

# Executor 层（vllm/v1/executor/） # multiproc_executor — 多进程并行（本地多 GPU） # ray_executor_v2 — Ray 分布式执行 # uniproc_executor — 单进程执行（调试/单 GPU） # Worker 层（vllm/v1/worker/） # cpu_worker / gpu_worker / tpu_worker / xpu_worker # ModelRunner 层（vllm/v1/worker/） # gpu_model_runner.py（v2 迁移中：vllm/v1/worker/gpu/model_runner.py）

engine_core.post_step(): 投机解码状态更新

post_step() 在 step_fn() 执行完毕后调用，负责将本轮推理产生的 draft token ids 同步回 scheduler，为下一轮投机解码（Speculative Decoding）做准备。

output_processor.process_outputs(): 后处理

这一阶段承担三个关键职责：

  1. Detokenize — 将 token ids 解码为文本
  2. Stop Check — 判断请求是否应该停止
  3. 创建 RequestOutput — 封装最终输出对象

停止条件详解

停止条件 检测位置 是否出现在输出中 说明
超出长度限制 Scheduler / Output Processor — 达到 max_tokens
EOS token GPU Sampler ✅ 在 token_ids 中 采样阶段直接检测
stop_token_ids GPU Sampler ✅ 在 token_ids 中 采样阶段直接判断
stop (strings) CPU Output Processor ❌ 被截断 需 detokenize 后做字符串匹配

⚠️ 注意区分：stop_token_ids 在 GPU 采样阶段就能检测到（Sampler 直接判断）；而 stop（stop strings）必须在 CPU detokenize 之后才能检测到，需要拼出文本再做字符串匹配。这就是为什么 stop strings 的处理在 output_processor.process_outputs() 中完成。

📝总结

整体流程可以概括为：

  1. 入口：llm.generate() → _run_completion()
  2. 预处理：格式化 + tokenize + 注册请求到 engine
  3. 引擎循环：反复执行 llm_engine.step()
  4. 核心三步：Schedule → Execute → Update
  5. 后处理：Detokenize + Stop Check + 封装 RequestOutput
  6. 返回：按 request_id 排序输出

关键边界：engine_core 负责调度和模型执行（GPU 侧），output_processor 负责 detokenize 和 stop 检查（CPU 侧）。stop_token_ids 在 GPU 检测，stop strings 在 CPU 检测。
