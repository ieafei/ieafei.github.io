scheduler.schedule() 内部流程

深入解析调度器如何为每一步推理分配 token 预算，追踪从接口定义到 running request 处理的完整逻辑

🎯背景与职责

scheduler.schedule() 是 engine_core.step_fn() 三步核心中的第一步，负责决定本轮推理中每个请求需要处理多少个 token。

其来源是 sched/interface.py 中定义的抽象接口 schedule()，由子类 Scheduler 具体实现。

核心输出：一个 request_id → num_tokens 的映射，即每个请求本轮需要处理的 token 数量。

不同请求类型的 num_tokens

请求类型 num_tokens 值 说明
新请求（prefill） len(prompt_token_ids) 首次进入，需要处理完整 prompt
自回归生成（decode） 1 每步只生成 1 个新 token
投机解码 / Chunked Prefill / Prefix Cache (1, len(prompt)) 之间 根据策略动态决定，可能是 1 到完整 prompt 长度之间的任意值

请求的核心属性

每个请求在调度器视角下只关注两个关键属性：

Request 核心属性
num_computed_tokens # 已完成计算的 token 数量（已经过 forward pass） num_tokens_with_spec # 包含 spec token 在内的总 token 数量 # = len(prompt_token_ids) + len(output_token_ids) + len(spec_token_ids)

调度目标：每个调度步中，调度器都会尝试为各请求分配 token，使 num_computed_tokens 能够追赶上 num_tokens_with_spec。

🗺️调度流程图（Running Request 处理）

ENTRY
scheduler.schedule()
遍历所有 running requests，为每个请求计算本轮应处理的 token 数
CHECK A
是否已达到 token 上限？
判断请求是否已经不需要再生成 token（最差情况估算）
条件：num_computed_tokens + 2 - num_output_placeholders
        >= num_prompt_tokens + max_tokens
→ 满足则 continue（跳过本请求）
CALC B
计算 num_new_tokens（初始值）
本轮需要处理的 token 数 = 目标总量 - 已计算量
num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens
CONSTRAINT 1
约束1：long_prefill_token_threshold
单步 prefill 不能超过配置的最长 token 阈值
if 0 < long_prefill_token_threshold < num_new_tokens:
    num_new_tokens = long_prefill_token_threshold
CONSTRAINT 2
约束2：token_budget（全局预算）
本步所有请求合计不能超过 token 总预算，分配后扣减预算
num_new_tokens = min(num_new_tokens, token_budget)
token_budget -= num_new_tokens
CONSTRAINT 3
约束3：max_model_len（模型最大长度）
防止 spec decoding 一次追加多个 draft token 时冲出模型长度边界
num_new_tokens = min(num_new_tokens, max_model_len - 1 - num_computed_tokens)
GATE
num_new_tokens == 0？
经过三重约束后若仍为 0，则跳过本请求；否则进入 KV Cache 分配
if num_new_tokens == 0: continue
else: 为该请求分配 KV Cache blocks

🔍逐步详解

CHECK A：token 上限判断

调度器在为请求分配 token 之前，首先判断该请求是否已经达到生成上限，无需再参与本轮调度：

if (request.num_computed_tokens + 2 - request.num_output_placeholders >= request.num_prompt_tokens + request.max_tokens): continue

这里的 +2 - num_output_placeholders 是一个"最差情况估算"，理解它需要区分两种调度模式：

调度模式 num_output_placeholders 含义 说明
同步调度 0 上一步 forward 已完成，token 已追加到 output_token_ids，scheduler 看到真实数量
异步调度 > 0 上一步 forward 还未完成，用 num_output_placeholders 表示"飞行中、即将产生但尚未到达"的 token 数

公式推导：num_computed_tokens + 2 - num_output_placeholders 等价于 (num_computed_tokens + 1) - (num_output_placeholders - 1)

最差情况推导（spec decoding 全部拒绝时）
num_computed_tokens + 1 # 前一步 forward 完成时，至少产生 1 个真实 sampled token # 即使所有 draft token 都被拒绝，主模型自己还是会采样出 1 个 token - (num_output_placeholders - 1) # num_output_placeholders 中最多有 (num_output_placeholders - 1) 个是 draft token # 剩余 1 个是必然产生的 sampled token = num_computed_tokens + 2 - num_output_placeholders

CALC B：num_new_tokens 初始计算

通过上限检查后，计算本轮需要处理的 token 数量：

num_new_tokens = ( request.num_tokens_with_spec + request.num_output_placeholders - request.num_computed_tokens )

直觉上：目标总量（含飞行中的 placeholder）减去已完成量，就是本轮还需要处理的量。

三重约束详解

约束1 — long_prefill_token_threshold：限制单步 prefill 的最大 token 数，防止一个超长 prompt 独占整个调度步的计算资源。

if 0 < self.scheduler_config.long_prefill_token_threshold < num_new_tokens: num_new_tokens = self.scheduler_config.long_prefill_token_threshold

约束2 — token_budget：全局 token 预算，控制本调度步中所有请求合计处理的 token 总量上限。每分配一个请求后立即扣减，保证总量不超标。

num_new_tokens = min(num_new_tokens, token_budget) token_budget -= num_new_tokens

约束3 — max_model_len：防止 spec decoding 场景下一次性追加多个 draft token 时超出模型最大序列长度。

num_new_tokens = min( num_new_tokens, self.max_model_len - 1 - request.num_computed_tokens )

⚠️ 为什么 spec decoding 特别需要约束3？普通自回归每步只生成 1 个 token，不会越界；但 spec decoding 一次性追加 N 个草稿 token（N 通常为 3~5），在接近 max_model_len 边界时，这 N 个 token 很容易一下子"冲出"边界，必须截断。

GATE：num_new_tokens == 0 的处理

经过三重约束后，若 num_new_tokens 降为 0（通常是 token_budget 耗尽），则跳过该请求，不为其分配 KV Cache blocks：

if num_new_tokens == 0: continue # 否则：为该请求分配 KV Cache blocks # （KV Cache 分配逻辑待补充）

📝总结

对每个 running request，schedule() 的处理逻辑可以概括为：

  1. 上限检查：用最差情况估算判断请求是否已完成，跳过无需调度的请求
  2. 初始计算：num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens
  3. 三重约束：依次限制单步 prefill 长度、全局 token 预算、模型最大长度
  4. 零值过滤：约束后为 0 则跳过，否则进入 KV Cache 分配

✅ 关键边界：num_output_placeholders 是异步调度的核心概念，代表"飞行中"的 token；num_tokens_with_spec 包含了 spec decoding 的草稿 token，是调度目标的上界。
